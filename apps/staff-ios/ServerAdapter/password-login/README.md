# Вход сотрудников по телефону и паролю CRM

Локальный кандидат `crm-staff-native-password-20261028-r2` совмещён с последним подтверждённым исходным кодом рабочей CRM `4db748e0236b4b294bca8171550f3cefed49a8db`. Кандидат не развёрнут. Самостоятельное iOS-приложение — `ru.temichevvet.staff`, версия 0.1.0 (2). Другие приложения и кабинет владельца не входят в выпуск.

## Поведение

`POST /api/auth/staff-login` принимает существующие `login` (телефон, совместимость с email), `password`, UUIDv4 `installationId` и необязательное название устройства. Пароль не сохраняется приложением. Сервер сначала проверяет пароль, активность сотрудника и разрешение приложения; затем автоматически регистрирует телефон и выдаёт обычные HttpOnly cookies. Отдельного создания учётной записи, назначения роли или приглашения нет. Директор определяется действующей ролью `director`.

Для внешнего доступа нужны прежние включённая политика клиники и проверенный шлюз. Сохраняются session guard, рабочие права, индивидуальные ограничения записи, 15 минут бездействия и отзыв телефона. Старый веб-маршрут `/auth/login` и его механизм доверия не меняются. Отдельный серверный endpoint предназначен для общего контракта нативных приложений; Android-клиент этим пакетом не меняется.

Пароль теперь служит достаточным основанием первого входа в приложение: одноразовое одобрение администратора не требуется. Пара идентификатора установки и сотрудника даёт стабильный серверный токен, подписанный HMAC с имеющимся секретом шлюза; приложение этот секрет не получает. В базе хранится только hash токена. Очистка cookies сохраняет идентификатор установки в Keychain, поэтому обычный повторный вход не создаёт новый телефон и не снимает отзыв. Это отзыв известной установки, а не запрет физического аппарата после полного сброса устройства. Существующий действующий cookie доверенного телефона переиспользуется. Отозванный совпадающий cookie и отозванный токен установки не восстанавливаются.

Вход ограничен 30 запросами на IP и 10 на нормализованную учётную запись за 10 минут. POST автоматически не повторяется. Подробности прав и история остаются общими с CRM. Настоящая серверная доставка APNs не включается этим пакетом.

## Состав

32 файла API/схемы относительно текущего сервера; точные SHA-256 — `Docs/current-server-candidate.json` в iOS-проекте и manifest пакета. Общие staff/chat/native-push контракты взяты из проверенного снимка; сервис груминга совмещён трёхсторонне через версию 365. Сохранены поправки текущего выпуска: начало/цена прежние, клиент получает «было / стало» и новое окончание.

SQL добавляет шесть таблиц общего чата/нативных уведомлений, nullable `InternalMessage.clientKey`, индексы и внешние ключи. Команд удаления, изменения существующих данных и миграции ролей нет. Клинические таблицы не пересоздаются. Для самого password login новые таблицы не нужны; они требуются остальным экранам ранее подготовленного приложения.

## Активация и откат

1. Заново проверить фактические API image/revision, состояние защищённых сервисов и отсутствие конкурирующего выпуска. Ожидаемый предыдущий API image ID указан в manifest. При расхождении пересобрать кандидат, не перезаписывать более новую версию.
2. Сделать свежую приватную резервную копию БД/файлов/настроек. Восстановить в изолированную среду без внешней доставки; применить добавочную миграцию, проверить новый и прежний runtime на копии. Локальные синтетические тесты этой проверки не заменяют.
3. Собрать `Dockerfile.api` от точного текущего образа, передав `BASE_API_IMAGE`. Prisma генерируется внутри унаследованной Linux-среды; проверка datamodel запрещает изменение прежних полей и перечислений. Darwin engine из локальной сборки не копируется. Проверить packet hashes, миграционный ledger и обратную совместимость.
4. Применить только новую миграцию с обычной фиксацией Prisma ledger и переключить только `clinic-crm-api`. Не менять PostgreSQL/Redis/MinIO/backup, Web, сеть, owner gateway или состояние других приложений. Настройки удалённого доступа и аккаунты не изменять скрыто; если политика выключена, отдельно показать это директору.
5. Проверить здоровье, фактическую версию, новый маршрут и сохранность защищённых сервисов; вход настоящего директора проверяется на его iPhone с его паролем. Не создавать тестовых пациентов/записей в рабочей базе. Затем выпустить соответствующую iOS-сборку в TestFlight.
6. При проблемах вернуть только предыдущий API image и настройки этого выпуска. Новые таблицы, история чата, колонка и клинические данные сохраняются; обычный откат не восстанавливает БД поверх новых рабочих данных.

Этот пакет не содержит паролей настоящих сотрудников, Apple signing keys, server secrets или резервных копий. Выполненные локальные проверки записаны в `Docs/password-login-http.json`, `Docs/http-acceptance.json` и `Docs/password-login-verification.json` iOS-проекта.
