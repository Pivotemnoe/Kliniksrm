# Общий контракт переписки сотрудников — v1

Ветка codex/staff-android-native, основа 813d2ab5. Дата: 28 октября 2026.
Изменения готовятся в этой копии. На рабочем сервере контракт пока НЕ установлен.
Android — основной клиент этого чата. Swift/iPhone-клиент здесь не разрабатывается.

## Общая история и авторизация

Источник истории — существующий InternalMessage CRM. Все клиенты используют одну cookie-сессию CRM, те же учётные записи и доверие удалённого устройства. Рабочие роли не меняются; администратор для чата не требуется. Активные коллеги включают CLINIC и GROOMING. Каталог содержит id, fullName, position, status и прежние role title/code для совместимости CRM. Телефоны, email, финансы и клинические карточки в чат-контракт не входят.

Старые REST маршруты сохраняются. Добавления обратно совместимы.

| Метод | Путь относительно /api | Назначение |
| --- | --- | --- |
| GET | /v1/internal-messages/recipients | Активные коллеги кроме текущего |
| GET | /v1/internal-messages/conversations | items: employee, lastMessage, unreadCount; totalUnread |
| GET | /v1/internal-messages?employeeId=UUID&limit=100&beforeId=UUID | История только пары текущий сотрудник ↔ employeeId, items по возрастанию, hasMore и nextBeforeId |
| POST | /v1/internal-messages | recipientId, body, clientKey (UUID v4, обязателен мобильным клиентам) |
| POST | /v1/internal-messages/conversations/:employeeId/read | throughId: последний реально отображённый входящий message id |

body — непустой текст после trim, до 4000 символов. Самому себе и неактивному сотруднику отправлять нельзя. clientKey фиксируется до отправки. Повтор с тем же ключом/адресатом/текстом возвращает ту же запись; другой текст или адресат с использованным ключом — 409. Старые CRM-запросы без clientKey работают как раньше.

Сообщение, квитанция и push-событие сохраняются одной транзакцией. Успех клиент показывает только после 2xx API. При потере ответа результат неизвестен: автоматического POST/очереди нет. Явная проверка истории и ручной повтор с прежним ключом безопасны.

throughId проверяется как входящее сообщение от указанного собеседника к текущему сотруднику. Прочитываются только сообщения до этой границы, новое одновременно пришедшее сообщение не теряется. Старый запрос без throughId сохраняет прежнее поведение CRM. GET истории ничего не прочитывает.

## Открытое приложение

Пока приложение видно, оно обновляет conversations и открытый thread раз в 8 секунд. Фон прекращает опрос. Автоматические GET и read receipts посылают заголовок X-TemichevVet-Passive: 1: только специально отмеченные маршруты не продлевают idle session. Все проверки срока, отзыва устройства, сотрудника и прав остаются обязательными. Активный вход, явная загрузка, отправка и остальные штатные действия сохраняют обычное поведение сессии.

Список диалогов и число непрочитанных обновляются для сообщений от ЛЮБОГО активного отправителя, без фильтра роли. При открытом диалоге сообщения добавляются по id; автопрочтение — только после отображения этой истории. Ни push, ни открытие списка не отмечают диалог прочитанным.

## Общие нативные устройства и события

| Метод | Путь относительно /api/v1/staff-app | Контракт |
| --- | --- | --- |
| GET | /native-push/config?platform=ANDROID&applicationId=… | available, provider: FCM/APNS, applicationId |
| POST | /native-push/devices | installationId UUID v4, platform ANDROID/IOS, applicationId, token, environment: PRODUCTION/SANDBOX (IOS), ответ id/expiresAt |
| DELETE | /native-push/devices/:id | Отмена только своей регистрации |
| GET | /native-push/events/:id | После входа: eventId, kind, conversationEmployeeId для собственного события |

Разрешённые applicationId и конфигурация транспортов задаются сервером; клиент не выбирает чужой topic/project. Android — FCM HTTP v1, iPhone — APNs HTTP/2 с отдельным key/topic. Общее событие INTERNAL_MESSAGE создаётся для каждого нового сообщения независимо от отправителя. В payload только eventId, kind и conversationEmployeeId; личный текст, имена и данные пациента не передаются. На экране блокировки — общий текст «Новое сообщение в CRM». Нажатие открывает соответствующий диалог после проверки входа.

Регистрация — отдельный ограниченный notification grant на 30 дней, привязанный к employee/session/trusted device. Истечение idle session требует входа перед чтением истории и не продлевается push-отправкой. Как в существующем PWA push, общий сигнал может доставляться по notification grant пока связанная сессия ещё существует; logout, удаление сессии, смена пароля/отзыв устройства отзывают grant. Перед отправкой повторно проверяются активность, staff_app.use/notifications, удалённое доверие, актуальность события и принадлежность получателю.

Запись отправки уникальна на пару event/device. ACCEPTED означает принятие транспортом, не показ на телефоне; UNKNOWN после неопределённого ответа автоматически не повторяется. Чтение/отзыв/смена настроек отменяют ещё не отправленные события. Каждое сообщение имеет отдельный event id, замены уведомлений между разными сообщениями нет.

## Текущая готовность

Контракт зафиксирован; реализация и тесты общего API/Android в работе.
Реальные FCM/APNs ключи, production backend deployment, физические устройства и межплатформенный обмен на двух настоящих приложениях пока не проверены. Синтетическая серверная приёмка не доказывает нативную доставку.

## Общий чат клиники

В доступных исходниках проверены раздел личной переписки StaffMessagesPage, StaffAlertsPopover и отдельный клиентский ClinicChatService. Канал сотрудников с общей историей там пока не идентифицирован. По уточнению пользователя создаётся отдельная общая сущность CRM; существующие личные сообщения, новости и оповещения сохраняются. История внешнего/старого канала автоматически не стирается и не импортируется без установления её источника.

| Метод | Путь относительно /api/v1/internal-messages | Назначение |
| --- | --- | --- |
| GET | /clinic | id, title, unreadCount, lastMessage |
| GET | /clinic/messages?limit=100&beforeSequence=… | Единственная общая история, items по sequence, hasMore, nextBeforeSequence, readThroughSequence |
| POST | /clinic/messages | body, clientKey UUID v4; адресат не нужен |
| POST | /clinic/read | throughId — последнее реально показанное сообщение общего канала |

Это один StaffClinicChannel и одна StaffClinicChatMessage на сообщение, без копий в личных диалогах. Поля сообщения: id, channelId, body, clientKey, sequence (десятичная строка), createdAt, sender (id/fullName/position/status). Каждый сотрудник имеет свой монотонный readThroughSequence. Авторские сообщения не добавляют автору непрочитанные.

Канал привязан к Organization. В существующей схеме Employee не имеет organizationId: автоматическое включение активных CLINIC/GROOMING сотрудников допустимо только при единственной организации в этой установке. При нескольких организациях требуются явные StaffClinicChatMembership; без привязки API отказывает, а не показывает глобальный чат. Клиент не передаёт чужой channelId/organizationId для чтения.

Одно новое общее сообщение создаёт отдельный event CLINIC_CHAT для каждого другого активного участника. Автор исключён. Payload имеет eventId, kind: CLINIC_CHAT и channelId. GET собственного native-push/events/:id подтверждает канал после входа. Открывать следует общий чат, личный conversationEmployeeId отсутствует. Настройки уведомлений, устройство и актуальное личное прочтение проверяются отдельно для каждого получателя.
