# Ассистент клиники — пакет внутреннего пилота и будущий выпуск

08.10.2026. Настоящие сообщения и публикация не входят в выполненный внутренний этап.

## Что готово

- Обязательная карточка администратора, ответственный, отложенные обращения, ручное подтверждение и переписка в CRM.
- Общий текстовый чат, устойчивые очереди при обрыве LAN/облака, подключение существующего MAX webhook и одноразовых ссылок.
- Выбор разрешённой услуги/даты, свободного времени и своего питомца; два согласия и атомарная запись в CRM. Гость оставляет заявку человеку.
- Напоминания зарегистрированного владельца **включены по умолчанию**. Можно выключить отдельный тип либо все. Сохранённое отключение имеет приоритет при миграции и повторной синхронизации.
- Контекстный черновик врача с источником и явным принятием, без назначения лекарств и автоматического сохранения.
- Отдельная страница `/assistant` на owner-gateway, без учётной записи персонала. Ссылка в личном кабинете появляется при включённом пилоте. Проверка текущего владельца закрывает прежнюю историю после выхода/смены аккаунта.

## Сборка и внутренняя проверка

Из корня проекта: `npm run assistant:build`. Команда выполняет typecheck и отдельный Vite bundle, затем сборку owner-gateway. Генерируемые HTML/JS/CSS находятся в `apps/owner-gateway/public/assistant` и копируются в `dist/public/assistant`; исходники — `apps/web/assistant.html`, `src/assistant-main.tsx`, `src/features/clinicAssistant`, `vite.assistant.config.ts`. Dockerfile gateway также собирает этот bundle. Генерируемые файлы не следует редактировать вручную.

Проверенный локальный QA URL: `http://127.0.0.1:4312/assistant`. Данные полностью вымышленные. Это не адрес для клиники. QA Docker tag: `temichevvet-owner-gateway:assistant-qa-20261008`, arm64. Образ собран и проверен без сети; production linux/amd64 образ пока не квалифицирован.

Результаты: `outputs/assistant-20261008/ACCEPTANCE.md` и `QA-REPORT.md`. Повторять платные вызовы модели или отправку провайдеру для чтения этих результатов не требуется.

## Кнопка обновлённого сайта

После отдельного разрешения на выпуск кнопка сайта может открывать первый origin owner-gateway, например:

```html
<a href="https://clinic.temichevvet.ru/assistant">Чат клиники</a>
```

Этот URL — подготовленная цель будущего выпуска, **публичный маршрут ещё не включался**. Разные локальные прототипы сайта не подменены и не опубликованы. Перед выпуском выбрать утверждённый исходник обновлённого сайта и проверить кнопку в его preview. Если сайт обслуживает чат через общий reverse proxy, `/assistant/*` и `/v1/public/assistant/*` должны вести в тот же gateway вместе с `/portal` и owner session cookie. Клинический LAN endpoint в браузер и публичный proxy не передавать.

Страница чата и кабинет работают на одном origin gateway. Это сохраняет действующий вход и не требует сторонних cookie. Iframe сейчас запрещён `frame-ancestors 'none'`/X-Frame-Options; не обходить эту политику. Возможный встроенный виджет — отдельное изменение с собственной проверкой сессий и CSP. В текущем пакете чат закрыт от поисковой индексации.

## Перед будущей публикацией

1. Сначала подтвердить текущие серверы и версии только чтением, доступность LAN и рабочего owner-gateway. Подготовить резервные копии и точные прежние образы API/web/gateway. Новый выпуск касается приложений API/web/gateway; PostgreSQL, Redis, MinIO, backup и тома не останавливать.
2. Сверить и применить новые миграции CRM и gateway после резервного копирования. Использовать штатный migrate deploy; не редактировать историю миграций, не пересоздавать базу. Миграция default-on сохраняет уже сохранённые opt-outs.
3. Собрать и проверить целевой linux/amd64 образ, реальные TLS/cookie/CORS/CSP, `/assistant` и все hash assets. Ключ OpenAI остаётся на существующем NL bridge; gateway token хранится только на сервере. Значения секретов не помещать в Vite env, браузер, журнал или release документ.
4. Проверить действующий MAX бот на одном контролируемом тестовом аккаунте: регистрация, одноразовая привязка, входящее сообщение, ответ CRM, блокировка и `/stop`. Webhook менять только как часть согласованного выпуска, с секретом и дедупликацией. Передача отдельной беседы и уведомления личного кабинета проверяются отдельно.
5. Выдать утверждённые адрес/режим/телефон клиники в CLINIC_ASSISTANT_APPROVED_*; отсутствующие ответы передаются администратору. Правила самостоятельной записи включать явно для разрешённых врачей, кабинетов и услуг. Проверить праздничный график, длительности и лимиты записи.
6. Включить CLINIC_ASSISTANT_ENABLED и необходимые AUTO_BOOKING/MODEL/REMINDERS флаги на соответствующих API/gateway только в согласованном выпуске. Профили владельцев уже default-on, но это не включает внешний транспорт во внутреннем QA. Наличие активной привязки MAX необходимо для доставки. По умолчанию модельный бюджет $1/сутки/$10/месяц относится только к этому пути, не к старому боту на том же ключе.
7. Принять реальные рабочие пути: сайт → CRM → администратор → ответ; запись и повтор/reload; перенос/отмена → отмена старого напоминания; default-on → отдельное отключение → повторный вход; один подтверждённый MAX результат. Убедиться, что администратор видит новую заявку поверх текущего раздела и не теряет ввод. DOM/health не заменяют проверку настоящего рабочего места.
8. При необходимости сначала выключить новые feature flags, сохранить необработанные очереди и журнал UNKNOWN, вернуть прежние приложения. Не удалять данные/таблицы и не пересылать UNKNOWN автоматически. Прежние сохранённые opt-outs не сбрасывать.

Это будущие release gates, а не выполненные production действия. Мониторинг каждые 15 минут остаётся остановленным по распоряжению пользователя.
