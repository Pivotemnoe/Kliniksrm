# Привязки расходников к услугам и товарам

## Работа в CRM

Раздел: **Склад → Привязки расходников** (`/stock/consumables`).

- **К услугам / К товарам:** поиск по всему каталогу, настройка одной или нескольких позиций, просмотр «было / станет» перед применением. «Добавить» сохраняет остальные прямые привязки; «заменить» заменяет прямой состав, сохраняя общие наборы и шприцы по объёму.
- **Общие наборы:** один состав для нескольких услуг и товаров. Изменение набора действует на новые выполнения всех подключённых позиций. Совпадающий прямой расходник заменяется набором; остальные прямые расходники сохраняются. Пересечение одинакового товара в разных общих правилах одной позиции запрещено.
- **Шприцы по объёму:** существующая настройка сохранена; прежний адрес `/stock/syringes` открывает эту вкладку.

Норма задаётся на одну единицу основной услуги/товара в **единицах списания** расходника. Например, 1 тест из упаковки на 50 тестов списывает 0,02 упаковки при корректном пересчёте в карточке. Не представимые с точностью складского учёта (0,001) нормы отклоняются с предложением использовать более мелкую складскую единицу. Диск для панели исследований нужно связывать с услугой панели, а не с каждым показателем отдельно.

Расходники списываются в существующих точках выполнения приёма/стационара и повторно клиенту не начисляются. Повторное сохранение не дублирует списание; корректировки количества и отмена счёта используют прежние нормы. В стационаре оплата при выписке не списывает уже использованные материалы повторно. Отмена ещё не выполненного плана ничего не списывает; правила отмены выполненных стационарных действий не расширены.

Права: `stock.read` для просмотра, `stock.manage` для изменений. Все новые изменения настроек записываются в аудит. Конкретные клинические привязки и нормы не создаются автоматически.

## Сохранность выполненных операций

Добавлены `ServiceConsumableRule` и `ConsumableUsageSnapshot`. Снимок состава и коэффициентов пересчёта создаётся при выполнении, а для прежних выполненных операций — перед изменением связанных настроек. Изменение нормы, состава набора или фасовки не пересчитывает прошлый расход; дальнейшая коррекция количества использует сохранённые коэффициенты. Снимок содержит только идентификаторы каталога и нормы, без медицинских данных.

Миграция `20261019000100_general_consumable_bindings` добавляет таблицы и ограничения; не изменяет существующие остатки, цены, услуги, товары и медицинские записи. Пустые таблицы не запускают массовый пересчёт истории.

## Проверки

- Сборка API, web typecheck, production web build.
- Основной набор: 510 успешно, 16 интеграционных проверок пропущено без отдельной БД, ошибок нет.
- Новые интеграционные сценарии на отдельной локальной PostgreSQL: 11 успешно. Проверены предварительный просмотр, массовая запись, общие наборы, корректировки, прежние нормы, фасовка, стационар, нехватка остатков и атомарный откат.
- Регрессия накладной на 100 строк, шприцев и ночных изменений оплаченного приёма на отдельных БД: 12 успешно.
- Проверка реальных HTTP-сессий на вымышленных пользователях: анонимный запрос 401, изменение с правами только просмотра 403, неверный ввод 400. Созданный через браузер набор сохранился после перезагрузки.
- Браузер: массовая настройка, ввод дроби через запятую, создание/повторное открытие общего набора, старый адрес шприцев, ширина 390 px без выхода страницы за границы.

## Установка

Перед миграцией нужна свежая проверенная резервная копия БД и конфигурации. Использовать образы точной версии, `SEED_ON_START=false`; применить миграции один раз и пересоздать только `api` и `web` через `--no-deps`. PostgreSQL, Redis, MinIO и backup не перезапускать. После установки проверить версии, health, новый JS-модуль, права и отсутствие новых ошибок. Ответ health не подтверждает состояние экранов всех рабочих мест.

После настройки общих наборов прежний API не поддерживает их семантику. Не выполнять автоматический откат версии или восстановление БД; исправлять вперёд после диагностики.
