# Коммерческая защита, поддержка и финальная приёмка

## Что доступно директору

Раздел **Настройки → Поддержка и лицензия** доступен только сотрудникам с директорскими правами. В нём можно:

- создать обращение и видеть журнал его обработки;
- приложить безопасный диагностический пакет только после отдельного согласия;
- открыть настроенный канал поддержки или email;
- увидеть код установки и код серверного компьютера;
- установить подписанную офлайн-лицензию;
- загрузить отчёт восстановления нового сервера и зафиксировать приёмку.

Директор редактирует организацию, филиалы, сотрудников, документы, финансы и другие данные через штатные настройки CRM. Редактирование программного кода из интерфейса не предусмотрено.

## Безопасная диагностика

Диагностический пакет не включает ФИО, телефоны, адреса, тексты приёмов, диагнозы, сообщения, пароли и токены. В него входят версия сборки, состояние резервных копий, архитектура, лицензионный статус и только общие количества записей. Экспорт записывается в журнал аудита.

Обычный экспорт журнала активности не следует отправлять как диагностический пакет: в нём могут быть имена сотрудников, IP и внутренние идентификаторы.

## Офлайн-лицензия

Режимы:

- `compatibility` — действующая клиника продолжает работать без блокировки;
- `advisory` — отсутствие или ошибка лицензии показываются директору, но работу не останавливают;
- `required` — рабочие разделы API доступны только с действующей подписанной лицензией; вход и раздел лицензии остаются доступны.

Лицензия подписывается Ed25519, привязывается к коду установки и SHA-256 коду Windows MachineGuid. Простое копирование базы, `.env` и лицензии на другой компьютер не проходит проверку сервера.

Закрытый ключ выдачи лицензий должен храниться вне Git, Docker-образов, флешек клиники и резервных копий CRM. В сборке и клинике нужен только открытый ключ. Для генерации ключей и выдачи лицензии предусмотрены локальные команды `npm run license:generate-keys` и `npm run license:issue`.

Ни одна офлайн-защита не делает установленное на чужом компьютере ПО абсолютно некопируемым для квалифицированного взломщика. Этот контур защищает штатное коммерческое распространение, случайное копирование и запуск комплекта в другой организации; юридическая лицензия и ограничение доступа к исходному коду остаются обязательными.

## Подлинность Docker-образов и флешки

GitHub Actions публикует API и web по неизменяемому digest и создаёт для каждого образа криптографическую build-provenance аттестацию GitHub. Проверка выполняется по digest, а не по изменяемому тегу `stable`.

При создании офлайн-комплекта рядом с `temichevvet-images.tar` записываются SHA-256 и `RELEASE-MANIFEST.txt`. Windows, Linux и macOS проверяют SHA-256 **до** `docker load`. Повреждённый или подменённый архив не загружается.

## Финальная приёмка нового сервера

1. Зафиксировать commit, версию выпуска, digests/аттестации образов.
2. На старом Windows-сервере создать полный комплект переноса на отдельный защищённый диск.
3. Проверить внешний и внутренние SHA-256.
4. Восстановить архив только в пустую базу нового Windows-сервера.
5. Автоматически сверить владельцев, животных, приёмы, вакцинации, записи, очередь, счета, оплаты, продажи, товары, остатки, движения, файлы, уведомления, сотрудников, задачи, документы, поставщиков, зарплатные периоды, бизнес-операции и обращения.
6. Открыть на новом сервере несколько реальных карточек, документов и файлов.
7. Загрузить `transfer-restore-report.json` в CRM и нажать «Принять сервер».

Принятие сервера не удаляет ничего на старом компьютере. Старый компьютер хранится выключенным как резерв до отдельного решения директора. Docker volumes старого сервера не удаляются.
