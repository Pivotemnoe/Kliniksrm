# PWA сотрудников TemichevVet

Первая версия: одно приложение `/staff/` для сотрудников клиники и грумеров. После входа сервер определяет кабинет и доступные действия. Используются действующие учётные записи и общая база CRM.

| Кабинет | Первая версия |
| --- | --- |
| Сотрудник клиники | Своё расписание и просмотр расписания клиники по существующим правам, смены, назначенные задачи и входящие сообщения; карточка записи с клиентом, питомцем и комментарием |
| Запись в клинику | Отдельно включается сотруднику при наличии `appointments.read/manage`; создание записи использует обычные правила расписания CRM |
| Грумер | Свой календарь, поиск клиента по полному телефону, добавление клиента и питомца, создание и перенос своей записи, отметки «Пришёл», «На процедуре», «Завершён», отмена и неявка |
| Уведомления | Клиника — входящие сообщения в приложении; грумер — события записей в приложении и Web Push при подключённом устройстве и настроенной доставке |
| Настройка | В CRM: «Настройки → Приложение сотрудников»; в PWA у уполномоченного сотрудника: «Профиль → Настроить возможности сотрудников» |

Для клиники запись с телефона по умолчанию выключена. Для грумера самостоятельное создание и перенос также включаются отдельно. Право включения требует действующих рабочих разрешений; настройка не назначает роль администратора и не открывает экономику. Склад, касса, смены и другие существующие рабочие права сохраняются.

Доступ к приложению и уведомления можно включать каждому сотруднику. Настройки хранятся как индивидуальные разрешения `staff_app.*` в существующей таблице переопределений. Изменения ролей и схемы БД для этой версии не требуются. У администратора груминга список настройки ограничен грумерами; управление всеми сотрудниками требует имеющихся соответствующих прав.

Записи создаются в обычных `Appointment` и `GroomingReservation`. Грумеру сервер выдаёт только его интервалы и проверяет исполнителя повторно при сохранении. Предложение времени связано с сотрудником и клиентом; подтверждение и перенос сохраняют существующие блокировки, контроль версии и уведомления CRM. Повтор клинической команды с тем же ключом возвращает исходную запись. Новые записи доступны в общем календаре; открытые экраны обновляют данные планово и после операций.

Сотрудник с удалённым доступом по-прежнему подключает доверенный телефон через действующий механизм CRM. Включение функции в приложении не заменяет привязку устройства. Для клиники удалённая запись разрешается только отдельной командой приложения; остальные ограничения удалённого доступа сохраняются.

## Установка и соединение

Для установки PWA нужен HTTPS; localhost допускается при разработке. Обычный адрес HTTP в локальной сети не обеспечивает полноценную установку и service worker. Вариант защищённого адреса для работы внутри клиники без внешнего канала требует отдельного выбора DNS/TLS; сеть и маршрутизаторы этой работой не перенастраиваются. [Требования PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

Приложение сохраняет записи после ответа CRM. При потере связи показывается состояние подключения или публичный экран отсутствия связи. Service worker контролирует только `/staff/` и кеширует только публичную страницу отсутствия связи. Ответы API, медицинские карточки, сеансы и команды записи не сохраняются в его кеше; фоновой очереди записи нет.

Push подключается по действию сотрудника на конкретном телефоне. Приватные детали записи открываются после входа. Персональное отключение уведомлений останавливает отправку на телефон, сохраняя историю событий в CRM. Фактическую доставку и установку на iPhone/Android необходимо отдельно принять на устройствах.

## Разработка и проверка

Изолированная рабочая копия создана от `c43e0e8c8dd46de80a4616072b1a8f9d2826d1c1`, установленной линии CRM. Незавершённое обновление количества госпитальных препаратов в пакет не включается.

Сборки:

```sh
npm run api:build
npm --workspace @clinic-crm/web run staff:build
npm run web:build
```

Локальная приёмка использует только схемы `staff_mobile_qa_20261028` в заранее известных синтетических БД на `127.0.0.1:55440`. Скрипт подготовки проверяет адреса, имя владельца схемы и `search_path`. Явный режим сброса разрешён только для этих помеченных тестовых схем. Таблицы данных создаются в этих схемах; для ограничений интервалов проверяется расширение btree_gist. Ограничения пересечений из штатных SQL-миграций устанавливаются отдельно, поскольку Prisma schema их не описывает.

```sh
STAFF_APP_QA_CONFIRM=isolated-synthetic node scripts/staff-app/prepare-local-qa.mjs
GROOMING_QA_DATABASE_PROFILE=staff-mobile-20261028 node --test --test-reporter=tap --test-concurrency=1 tests/staff-mobile-pwa.integration.test.mjs tests/remote-readonly-shifts.test.mjs tests/grooming-crm.integration.test.mjs tests/grooming-staff-pwa.integration.test.mjs
node tests/helpers/staff-mobile-preview.mjs
npm --workspace @clinic-crm/web run staff:dev
```

Для просмотра собранной версии вместо `staff:dev` используется `npm --workspace @clinic-crm/web run staff:preview` на том же локальном порту. Одновременно запускается только один веб-сервер показа.

Полный набор проверок начинается с пустого клинического профиля. После ручного показа или предыдущего полного прогона остановите оба локальных helper и выполните подготовку с `STAFF_APP_QA_CONFIRM=isolated-synthetic STAFF_APP_QA_RESET=synthetic-schema-only`; этот режим удаляет только две помеченные схемы вымышленной приёмки. Без чистого профиля проверка автономности груминга обнаружит оставшиеся клинические примеры, что не является результатом проверки приложения.

Локальный показ: `http://127.0.0.1:4251/api/__qa/session/groomer` и аналогичные профили `doctor`, `doctor-booking`, `director`. Вход тестового показа существует только в отдельном helper, не входит в приложения и использует собственное имя cookie. Доставка во внешние каналы отключена. Данные вымышленные.

## Пакет и активация

`Dockerfile.web` накладывает проверенные сборки основной CRM и PWA на закреплённый текущий web-образ. Существующие точки входа груминга, гостиницы и прежние статические ресурсы сохраняются в базовом образе. `Dockerfile.api` обновляет скомпилированный API без изменения схемы и зависимостей.

Для будущего включения нужны свежая проверка целевых API/web-образов и состояния служб, резервная копия настроек доступа, установка только согласованных компонентов и приёмка с реальных телефонов. Ни сборка, ни локальная приёмка не активируют приложение на TECNO. Предыдущие CID/startup-guards госпитального кандидата не подходят этому выпуску и не изменяются.

## Android и iPhone

Следующий этап может использовать этот React-интерфейс и API в [Capacitor](https://capacitorjs.com/docs). Отдельно потребуются платформенные подключение, сеансы, уведомления, кнопка «Назад», сборки, подпись и проверка на устройствах. Нативные приложения и публикация в магазинах в эту первую PWA-версию не входят.
