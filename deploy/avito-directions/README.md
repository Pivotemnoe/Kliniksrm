# Авито: отдельные направления и переход к сайтам

Разделы «Клиника», «Зоогостиница», «Груминг» фильтруют переписку, заявки и статистику на сервере. Выбранное направление хранится в URL. «Без направления» сохраняет видимость непривязанных объявлений; бот там не отвечает. Клиентские записи не создаются в Авито: клиническую заявку подтверждает администратор, бронь зоогостиницы оформляется на сайте. Груминг остаётся без онлайн-записи до настройки реальных специалистов и смен.

API читает сведения собственного модуля направления; прайс клиники в ответы груминга и гостиницы не попадает. Перед отправкой ответа повторно проверяются доступность записи и тарифы. Изменение условий отменяет устаревший ответ. Привязка объявления распределяет старую непривязанную переписку, сохраняя управление сотрудником; автоматические ответы в истории не возобновляются.

## Проверки

- `npm run api:build`, `npm run web:typecheck`, `VITE_API_BASE_URL=/api npm run web:build`.
- Правила: `node --test tests/avito-pet-services.test.mjs tests/avito-policy.test.mjs tests/avito-availability.test.mjs tests/avito-clinic-dialogue-rules.test.mjs tests/avito-crm-knowledge.test.mjs`.
- Интеграция на отдельной одноразовой PostgreSQL: URL разрешён только для `127.0.0.1:55449/avito_directions_qa_20261021`; все контакты и диалоги синтетические, транспорт Авито подменён. Миграции применяются только к этой тестовой базе. В выпуске нет новых миграций.
- Ручная браузерная приёмка выполняется с ролью администратора: смена направления без перезагрузки документа, заявки отдельно, восстановление после reload, переход к исходному диалогу, мобильная ширина.

## Обратимый выпуск

`prepare-context.mjs` требует чистые сохранённые исходники и точные предыдущие API/Web images. В API накладываются только три модуля (9 скомпилированных файлов). Подготовка через существующий проверенный API release runner создаёт свежую резервную копию, проверяет восстановление в отдельном PostgreSQL без сети и квалифицирует candidate без доступа к рабочей БД. Переключается только `api`.

После проверки API создаётся свежий Web manifest по текущим конфигурационным hashes и image IDs. Web runner использует только что проверенную восстановлением копию API-выпуска. Переключается только `web`, старые assets сохраняются в существующем томе. Остальные контейнеры защищены проверкой идентичностей.

`configure.cjs plan` ничего не изменяет. `apply --execute` требует точную версию настроек, сверяет своё объявление гостиницы через Авито и сохраняет отдельную ревизию с аудитом директора. Клинический профиль, объявления, расписание, ночной тариф и таблица программ сохраняются. Полный before snapshot записывается в каталог резервной копии с ограниченными правами. Новое объявление груминга не выдумывается и автоматически не публикуется. Размещения и платные продления этот выпуск не выполняет.

Порядок отката: (1) восстановить настройки через `configure.cjs rollback --execute` по точной afterVersion/afterHash, (2) откатить Web через `run-web.ps1 -Mode Rollback`, (3) откатить API через `release-api.ps1 -Mode Rollback -Execute`. Сначала проверяются точные candidate IDs и отсутствие чужих изменений. Рабочие клинические записи и база при откате не восстанавливаются из старой копии. Сохранённая история переписки не удаляется.
